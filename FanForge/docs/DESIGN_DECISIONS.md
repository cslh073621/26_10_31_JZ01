# FanForge设计决策记录

本文件记录已经确认的设计原则、当前实现状态和后续模块必须遵守的约束。讨论形成明确结论后应更新本文件，不能只保留在对话中。

状态说明：

- `已确认并实现`：规则已经进入模板、清单或校验工具。
- `已确认未实现`：规则已经确定，但对应生成器模块尚未开发。
- `待审核`：只有方向性讨论，不能直接作为生成规则。

## 1. 生成器总体结构

状态：`已确认并实现初版`

- 当前首先支持HS16P2811。
- 应用内部只有一个权威HS2811核心模板。
- 用户配置和AI均不能选择历史项目或替换核心模板。
- 历史成熟项目只用于提取、验证和回归测试。
- 项目配置只描述芯片、封装、脚位、硬件和功能需求。
- 相同生成器版本加相同配置必须生成字节级相同的源码。
- 不支持的组合必须停止生成，禁止让AI临时补写重点函数。
- 功能模块和模板逐项提交用户审核，确认后才进入下一模块。

### 最终应用层目标

状态：`已确认，持续实现`

- 最终用户入口不是选择一套完整项目模板，而是选择芯片、封装、物理脚位和原子化功能参数。
- 原子化功能包括但不限于电机类型与控制方式、档位范围、按键动作、充电接口、电量系统、显示硬件与页面策略、制冷、LED、雾化、编码器、滑动变阻器和睡眠唤醒。
- 每个功能模块只提交自身的 GPIO、PWM、ADC、时间资源、状态、动作、联锁和安全时序需求；公共规划器统一解决脚位路由、寄存器配置、资源冲突和跨模块约束。
- `ADC_Sample()`、`mode_change()`、`KEY_deal()`、`show_mode_deal()`、`file_sleep_mode()`等成熟函数保留固定职责和代码风格，由确定性规则填充，不允许前端、配置或AI自由生成重点业务函数。
- 配置预设不是底层模板。现有`configs/*.json`只作为快捷填参、成熟组合示例、回归夹具和验收基线；新增预设不得复制一套新的生成逻辑。
- 同一组原子配置无论从CLI、桌面前端还是AI调用，都必须进入同一解析器、资源规划器和唯一核心模板，产生相同结果。
- 如果需求无法由当前原子模块表达，应先扩展模块契约、规划规则、测试和文档；禁止用新增整套模板、特殊项目分支或生成后手工补代码绕过。
- 当前仍有部分经典产品参数集中在大配置预设中，这是过渡状态，不代表最终架构。后续开发应优先把可复用差异下沉为原子参数和统一规划规则，而不是继续堆叠项目型模板。

## 2. HS2811标志位存储

状态：`已确认并实现`

- HS2811直接支持原生`bit`类型。
- 时间标志和产品布尔状态统一使用原生`bit`。
- 禁止使用`bit_flag`联合体和`flag.bits.bit0`等模拟位写法。
- 其他不支持原生`bit`的平台以后由对应芯片适配层处理，不能污染HS2811模板。

## 3. T1初始化函数命名

状态：`已确认并实现`

- HS2811系统时基实际使用T1，因此函数统一命名为`timer1_init()`。
- 不再沿用从其他平台遗留的`timer0_init()`名称。
- 历史证据文件保留原项目真实名称，不修改统计结果。

## 4. 系统主频与PWM默认值

状态：`已确认并实现`

- HS2811当前默认主频为16MHz。
- PWM默认使用16MHz作为时钟源。
- 无刷升压PWM默认频率为250kHz。
- 16MHz、1分频、250kHz对应64个计数周期，因此`T3PL = 64 - 1 = 63`。
- 用户以后可以输入其他目标频率，例如120kHz。
- PWM周期和占空比换算必须在生成器中完成，最终固件只保留常量寄存器值，不能让MCU运行时执行除法。
- 无法精确得到目标频率时，生成器必须报告实际频率和误差。
- 是否接受近似频率以及允许误差范围仍需在PWM模块审核时确定。

PWM周期基本计算：

```text
period_count = round(pwm_clock_hz / target_frequency_hz)
period_register = period_count - 1
actual_frequency_hz = pwm_clock_hz / period_count
```

以120kHz为例：

```text
period_count = round(16000000 / 120000) = 133
T3PL = 132
实际频率约120300.75Hz
```

## 5. PWM资源由功能模块声明

状态：`已确认并实现`

- PWM资源的生成方式与时间标志和ADC资源相同。
- 风扇、雾化、加热等功能模块分别声明需要的PWM角色、目标频率、占空比范围、物理脚位角色和启停顺序。
- 用户只选择功能、工作参数和对应物理脚位，不直接填写PWM通道及路由寄存器。
- 生成器汇总全部PWM需求后，统一分配定时器、通道、周期寄存器、占空比寄存器和路由寄存器。
- 用户输入物理脚位前必须选择具体芯片封装，例如SOP16、SOP14或QFN16。
- 生成器内部建立“物理脚位 -> GPIO -> PWM通道 -> 路由寄存器”的固定能力表。
- 用户只输入功能脚位，不直接填写`PWMSEL`、`PWMSEL1`、PWM通道和占空比寄存器。
- 生成器根据脚位能力自动生成GPIO方向、PWM路由、周期、占空比和通道使能配置。
- 使用`T3PWM4`等通道时必须正确选择对应路由寄存器，不能把`PWMSEL1`错误写成`PWMSEL`。

无刷电机资源角色：

```text
FAN_ON：普通GPIO，先开启并保持电机负极导通
PWM_FAN：硬件PWM，控制升压电路
启动：FAN_ON开启 -> 等待约10ms -> PWM_FAN开启
关闭：PWM_FAN关闭 -> 等待约10ms -> FAN_ON关闭
```

有刷电机资源角色：

```text
FAN_ON：硬件PWM，控制电机负极
PWM_FAN：不参与风速PWM并保持安全状态
```

有无刷兼容模式必须同时验证：

- `PWM_FAN`脚支持无刷所需PWM通道和上电检测。
- `FAN_ON`脚支持有刷所需PWM通道。
- 两套模式使用的GPIO和PWM路由均成立。

必须检测的资源冲突包括：

- 物理脚位不支持所需PWM。
- 两个功能占用同一物理脚位。
- 两个功能占用同一PWM通道。
- 共用同一周期寄存器的PWM功能要求不同频率。
- 无刷250kHz和雾化108kHz被错误分配到同一PWM定时器周期。
- 有刷模式的`FAN_ON`脚没有硬件PWM能力。

冲突时必须停止生成并说明原因，不能自动换成未经审核的方案。

最终固件仍生成直接寄存器语句，不保留运行时PWM资源表，也不在MCU中动态分配PWM。

## 6. GPIO资源由功能模块声明

状态：`已确认并实现`

- 公共GPIO初始化函数统一命名为`GPIO_Init()`，不再沿用职责不准确的`KEY_Init()`。
- 按键、拨片开关、充电检测、风扇、制冷、雾化、LED、数码管和硬件检测模块分别声明需要的GPIO资源。
- 用户配置负责把功能角色绑定到物理脚位，例如`FAN_ON -> 7脚`，不直接填写`TRISA`、`PAHCON`等寄存器值。
- 生成器根据芯片和封装能力表，把物理脚位转换成端口位和对应寄存器掩码。
- GPIO公共模块汇总需求后统一生成端口初值、方向、上下拉、开漏、模拟/数字模式和唤醒配置。

每个GPIO需求至少应声明：

- 功能角色和物理脚位。
- 输入、输出、模拟、PWM或允许复用的类型。
- 上电安全状态。
- 正常运行状态。
- 睡眠状态。
- 唤醒源要求。
- 是否需要在全亮自检期间临时切换成输入上下拉进行硬件检测。
- 临时检测结束后的恢复状态。

生成器必须检查：

- 同一物理脚位是否被不兼容功能重复占用。
- 输入上下拉是否与外部电路和有效电平冲突。
- 模拟功能是否错误保留数字输出。
- 睡眠状态是否遗留PWM、升压、LED、制冷或不必要上下拉。
- 唤醒脚是否具备对应端口唤醒能力。
- LED与按键、INSERT等复用脚是否存在经过审核的固定扫描方案。
- 共享脚没有对应成熟复用模块时必须停止生成，不能自动拼接。

最终固件仍生成成熟项目风格的直接代码：

```c
PORTA = ...;
TRISA = ...;
PAHCON = ...;
PADCON = ...;
ADPCON = ...;
```

不能在MCU运行时遍历GPIO配置表。

## 7. T1系统时基自动计算

状态：`已确认并实现`

- `timer1_init()`不能固定复制某个历史项目的`T1CON/T1TH/T1TL`。
- 生成器根据系统主频、T1时钟源、分频和目标基础周期计算重载值。
- 大部分普通项目的目标是稳定产生1ms系统标志。
- 没有高频功能时，可以让T1直接产生1ms中断。
- 存在数码管高频扫描、软件PWM、7+3调节、单线通信或步进电机时，可以采用更短基础周期，再通过子计数器派生1ms。

基本计算：

```text
timer_count = timer_clock_hz * target_period / prescaler
reload_value = 65536 - timer_count
T1TH = reload_value高8位
T1TL = reload_value低8位
```

生成报告必须包含：

- 系统主频。
- T1实际时钟源。
- T1分频。
- 重载值。
- 基础中断周期。
- 1ms标志的派生方式。

## 8. 时间标志和计数器生成

状态：`已确认并实现初版`

- 功能模块声明需要的时间周期，用户不需要手动声明`time_xxx_flag`和`time_xxx_cnt`。
- 生成器自动建立原生`bit`时间标志。
- 生成器自动建立对应计数器。
- 生成器根据周期选择合适的上级时间节点，例如从10ms派生200ms、350ms，从500ms派生3s、5s。
- 生成器自动把计数器累加和到期判断插入`time_flag_deal()`的固定位置。
- 长时间周期优先通过分层计数实现，避免无必要的宽计数变量和运行时除法。

相同周期不代表一定能够共用计数器：

- 周期相同且相位、重置条件和用途完全相同，才允许共用。
- 按键窗口、低电闪烁和风扇慢调节即使都是200ms，只要重置条件不同，就必须使用独立计数器。
- 功能模块必须同时声明计时器的启动、停止和清零条件，不能只声明周期。

如果T1基础周期不是1ms，`time_10ms_cnt`只能在真正派生出1ms时累加，不能在每次高频T1中断中直接累加。

初版实现范围：

- 当前 T1 基础周期固定为直接 1ms。
- 功能模块的时间请求按周期、相位和复位语义合并。
- 自动生成原生 `bit` 标志位、`u8` 计数器、ISR 累加和 `time_flag_deal()` 分层代码。
- 采用 1ms、10ms、500ms、1min 成熟层级，支持 1ms 到 4h。
- 只作为父时基的内部节点不生成无用途标志位。
- 同周期但不同相位或复位语义的请求生成独立计数器。
- 亚毫秒高频时基和业务模块自动插入复位语句尚未实现。

## 9. ADC资源由功能模块声明

状态：`已确认并实现初版`

- ADC资源的生成方式与时间标志资源相同。
- 用户不单独选择ADC通道、累加变量或处理函数。
- 用户只选择产品功能，并为需要外部ADC的功能指定物理脚位。
- 电量、风扇保护、AD按键、滑动变阻器等功能模块分别声明自己需要的ADC资源。
- 生成器汇总全部模块需求后，统一生成`ADC_Init()`、`ADC_Sample()`、通道轮询、变量、滤波和结果分发。

功能模块的ADC资源声明至少应包含：

- ADC资源名称和用途。
- 内部通道或外部物理脚位角色。
- ADC参考电压和时钟要求。
- 通道切换后的废弃样本数。
- 有效累加次数和平均方式。
- 结果更新周期。
- 对应的成熟处理分支。
- 初始化、风扇关闭和睡眠唤醒时需要清除的计数器。

生成器必须完成：

- 根据封装把物理脚位转换成模拟通道和`ADPCON/ADPCON1`配置。
- 验证脚位是否支持ADC。
- 合并能够明确共享的同源采样结果，例如风扇固定电压调节和AD_FAN超压保护。
- 对不同物理信号、不同参考电压或不同复位语义的需求保持独立。
- 检查ADC通道、脚位复用、参考电压、采样周期和累加宽度冲突。
- 计算累加最大值，禁止`u16`累加溢出。
- 只生成实际被功能模块请求的通道、变量和处理分支。

职责边界：

- ADC公共模块只负责初始化、采样、废样、累加、平均、通道轮询和结果分发。
- 电量模块负责`v_bat_deal()`及充放电追赶。
- 风扇模块负责固定电压调节或固定占空比超压保护。
- 输入模块负责AD按键或滑动变阻器的成熟处理逻辑。
- ADC公共模块不能自行发明各功能的业务判断。

初版实现范围：

- 支持外部物理 ADC 脚和内部 AIN12 `VDD/4`。
- 支持功能模块声明扫描顺序、参考电压、ADC 时钟、废样、一次平均、二次平均、结果变量和复位语义。
- 自动生成多通道 `ad_channel` 轮询、`ADM/VREFH/ADR` 切换、结果变量和初始化/睡眠清零。
- 相同来源和采样语义的请求共享结果，不同语义保持独立。
- 当前各通道必须共享一次废样数和一次平均数，保持成熟项目紧凑的共享计数结构。
- 电量、AD 按键等业务逻辑仍由后续独立模块生成。

## 10. 显示策略与模式收敛的生成关系

状态：`已确认并实现初版经典产品策略`

生成阶段不能让已经生成的`mode_change_show()`源码再向`mode_change()`提供信息，也不能解析前一个函数的C代码来生成后一个函数。正确结构是：

```text
功能模块状态和事件
        +
唯一显示策略模块
        ↓
统一项目状态契约
        ├── 生成mode_change_show()
        ├── 向mode_change()生成器提供显示覆盖和取消规则
        ├── 申请显示所需时间标志和计数器
        └── 生成show_mode_deal()所需页面状态
```

显示策略模块需要同时声明：

- 使用的显示状态变量，例如`show_mode`、`step_cnt`和显示切换标志。
- 开机、调档、插入充电器、拔出充电器、低电和关机等事件对应的显示序列。
- 哪些事件开始或重启显示计时。
- 哪些最终产品状态必须取消当前显示序列。
- 需要向`mode_change()`插入的显示收敛规则，例如风扇关闭时清除`step_cnt`。
- 需要向时间资源生成器申请的3s、5s等独立计时资源。

`mode_change()`生成器从统一项目状态契约中同时接收：

- 风扇、充电、低电、制冷等功能模块提供的状态约束。
- 显示策略模块提供的显示取消、强制页面和计时复位规则。

两个函数生成器消费同一份已经解析好的状态契约，彼此之间不存在源码级依赖和循环生成关系。

运行阶段继续保留成熟项目的调用关系：

- 保留成熟项目的固定调用顺序：`mode_change_show()` -> `mode_change()` -> `show_mode_deal()`。
- `mode_change_show()`根据时间标志推进显示步骤，更新`show_mode`、`step_cnt`和显示切换标志。
- `mode_change()`读取当前显示阶段和最终产品状态，执行低电、关机、插拔充电等强制收敛。
- `mode_change()`拥有最终覆盖权，可以清除`step_cnt`并强制切换或关闭显示，防止已经失效的显示流程继续运行。
- `show_mode_deal()`只读取收敛后的最终状态并生成`Data[]`显示缓存。

这三个函数形成顺序管线：

```text
输入模块改变产品请求状态
        ↓
mode_change_show推进定时显示阶段
        ↓
mode_change执行最终限制和覆盖
        ↓
show_mode_deal生成显示缓存
```

职责限制：

- 其他功能模块不能各自在`mode_change_show()`中插入页面判断。
- 唯一显示策略模块提供完整的`mode_change_show()`和`show_mode_change()`逻辑。
- 风扇、充电、按键等模块只能提出开始显示序列的请求。
- 各功能模块向`mode_change()`提供状态约束，由生成器按照固定优先级组合。
- 不得在未同步处理`show_change_flag`和`step_cnt`的情况下擅自把`mode_change()`移动到`mode_change_show()`之前，否则可能产生计数下溢或关机后重新亮屏。

`show_mode_change()`的生成规则：

- 由唯一显示策略模块完整生成，不由多个功能模块拼接。
- 负责启动或重启当前显示序列，并清除该序列使用的时间标志和计数器。
- 风扇、按键、充电等模块只提出“开始显示档位”等显示请求，不直接操作显示计数器。
- 显示策略模块向时间资源生成器申请对应计时资源，并保证函数中的复位语句与实际生成的计数器一致。

显示生成必须分成硬件和行为两层，并在生成前确定：

```text
显示硬件配置
    ├── 无角标、双角标或三角标
    ├── 每个角标的实际语义
    ├── Data[]位定义
    └── 灯脚和LED矩阵映射

显示行为策略
    ├── 常态显示档位或电量
    ├── 开机和调档后的页面顺序
    ├── 充电时的默认页面
    ├── 低电闪烁对象
    └── 充电闪烁对象
```

双角标或三角标不能只按数量推断功能，必须明确每个物理角标的语义。例如：

- 闪电标和百分号。
- 制冷标和百分号。
- 风扇标、雾化标和百分号。
- 没有闪电标时，是否明确要求用百分号表示充电闪烁。

角标配置必须使用可变长度列表，不能固定成只有`icon_1`和`icon_2`两个字段。当前明确支持：

- 无角标：空列表。
- 双角标：两个角标定义。
- 三角标：三个角标定义。

例如三角标：

```yaml
icons:
  - id: fan_icon
    role: fan
  - id: mist_icon
    role: mist
  - id: percent_icon
    role: percent
```

角标数量、物理映射和语义分别验证，不能因为是三角标就默认固定为某三种功能。

生成器必须验证行为策略没有引用灯板不存在的角标。不存在闪电标时不能自行改为百分号闪烁，只有产品配置明确选择这种行为后才能生成。

函数职责固定为：

- `show_mode_change()`：启动或重启页面序列并清除对应计时资源。
- `mode_change_show()`：根据时间标志推进档位页、电量页和常态页。
- `show_mode_deal()`：根据当前页面生成数字和角标，并处理末位、双位、闪电标、百分号或功能标的闪烁。
- `smg_188_scan()`：只根据固定灯板映射把`Data[]`输出到物理灯脚，不处理充电、低电和页面业务判断。

因此更换数码管灯板只影响硬件映射和角标能力，更换显示时序只影响显示策略，二者不能混在同一个代码模块中。

## 11. 输入事件与`KEY_deal()`生成

状态：`已确认并实现数字按键基础策略及AD按键短按/双击/长按`

输入处理分成两个层次：

```text
输入硬件模块
    └── 生成KEY_CHECK()所需的消抖、长短按、双击或编码器事件

产品操作映射
    └── 统一生成KEY_deal()，把已确认事件映射为产品请求状态
```

- 单按键、双按键、AD按键、编码器和拨片开关模块负责产生规范化输入事件。
- 风扇、制冷、雾化、照明和摇头模块只暴露可执行动作和目标状态。
- 唯一的产品操作映射生成器根据需求生成完整`KEY_deal()`，不能让各功能模块任意插入代码块。
- `KEY_deal()`只消费事件并改变请求状态，不复制低电关机、充电限制和公共关闭后果。
- 功能依赖和最终限制继续由`mode_change()`统一收敛。
- 双击窗口、长按周期和连续调档周期向时间资源生成器提出独立需求。
- 生成器必须固定事件处理优先级，避免短按和双击同时触发、KEY2改变KEY1方向等跨按键污染。
- AD按键只有明确配置`double_action`时才延迟单击；未启用双击的旧配置不生成点击计数、窗口计时或额外睡眠条件。
- 双击以第二次有效松手确认，第一次单击在窗口到期后才执行；长按事件会清除同一按键的待定单击和窗口。
- 每个可双击按键独占可复位时间资源，两个按键同时拥有双击动作时不能错误共用计数器。
- 连续加减档长按沿用成熟重复节奏，开关机、制冷和LED等长按动作只触发一次。

## 12. `file_sleep_mode()`生成

状态：`已确认并实现初版经典产品睡眠策略`

`file_sleep_mode()`采用多模块资源汇总，但必须由唯一睡眠生成器按照固定阶段组合：

```text
各功能模块声明睡眠需求和阻塞条件
        ↓
统一睡眠计划
        ├── 生成睡眠资格判断
        ├── 生成睡眠前硬件关闭
        ├── 生成GPIO上下拉和唤醒配置
        ├── 生成外设关闭和sleep指令
        └── 生成唤醒恢复和稳定保护
```

功能模块可以声明：

- 当前状态是否阻止睡眠，例如充电、照明、未完成按键窗口或显示提示。
- 睡眠前必须完成的动作，例如步进电机回原点。
- 睡眠时对应GPIO的方向、电平和上下拉。
- 是否需要保留为唤醒源。
- 睡眠时必须关闭的PWM、ADC、升压、制冷、雾化、显示和通信外设。
- 唤醒后需要清除的采样、输入、保护和通信状态。
- 唤醒后禁止立即再次睡眠的稳定时间。

固定职责边界：

- 正常关风扇、低电关机和功能连锁仍由`mode_change()`处理。
- `file_sleep_mode()`只在最终状态已经允许睡眠后，完成硬件低功耗配置和唤醒恢复。
- 需要时间才能完成的回原点等动作必须先成为睡眠阻塞条件，不能在关闭WDT后阻塞等待。
- GPIO、PWM、ADC和时间模块向睡眠生成器提供各自的睡眠状态，睡眠函数不能自行猜测寄存器。
- 同一项目最终只生成一个`file_sleep_mode()`，不能由多个功能模块各自提供睡眠函数。

## 19. 旋转编码器输入

状态：`已确认并实现首版`

- 制冷支持成熟的“风扇开启期间按键切换”和直接随风扇同步两种确定模式；无论哪种模式，风扇关闭都不能留下制冷输出。
- 充电是否允许制冷由配置决定，不再固定写死。默认禁止，保持现有经典项目行为。
- LED首版只开放不占额外PWM资源的`fan_sync`、`on_off`和`on_off_flash`。多档PWM亮度以后必须作为独立PWM资源模块审查，不能混入本次数字输出模板。
- 独立LED动作复用既有AD按键消抖和事件消费结构，不增加第二套按键状态机；独立LED开启时阻止睡眠。
- 全亮自检会拉高`LED_ON`，制冷输出保持关闭，避免自检期间制冷片连续工作。

## 24. 充电状态输入模块

状态：`已确认并实现首版`

- 充电接口模块只负责声明输入脚、有效电平、上下拉、睡眠唤醒和状态表，不接管成熟电量映射、追赶或显示业务。
- `chrg_stdby_active_low`保留原有成熟结构：两脚均使用内部上拉，CHRG低为充电，CHRG高且STDBY低为充满，两脚均高为未插入。
- `insert_active_high_chrg_active_low`使用INSERT内部下拉、高有效和CHRG内部上拉、低有效；只有INSERT为高时才解释CHRG状态，避免未插入时CHRG残余电平误判。
- 两种接口统一输出`insert_flag`、`charge_on_flag`和`charge_max_flag`，后续`mode_change()`、`v_bat_deal()`和显示代码继续消费同一状态契约。
- `none`不申请充电GPIO、充电状态位和充电追赶计时资源；放电映射、低电关机和放电追赶继续保留。
- 旧`classic_product.charging_kind`只用于兼容已有配置。新项目使用`features.charging`，冲突配置在生成期拒绝。

## 25. 188灯板有向映射

状态：`已确认并实现首版`

- 188灯板由显示模块声明逻辑段到有向灯脚组合，不允许产品业务代码直接拼接新的扫描分支。
- `positive/negative`使用`IO_LED_n`序号，物理脚位继续由公共GPIO绑定，段位关系不和SOP16物理脚号耦合。
- 百位两段、十位七段和个位七段是必需信号；百分号、制冷、充电、风扇、雾化和辅助角标使用`Data[0]`剩余位。
- 当前扫描方式固定为常态输出高、未点亮阳极切输入、当前阴极拉低，保持成熟项目的低微亮结构。
- 生成器拒绝缺段、未知信号、越界灯脚、同脚正负极和重复有向组合；反向组合视为另一颗合法LED。
- 旧五线双角标预置继续生成原有源码；自定义配置只替换段位和角标连接，不改变显示函数边界、1ms扫描位置、页面时序或原子缓存更新。

## 26. 显示页面时序参数化

状态：`已确认并实现首版`

- 页面策略和灯板映射保持分层；页面策略不读取或改写有向灯脚关系。
- 旧`gear_3s_battery_3s_gear`策略保留原有共用3s标志位和生成源码，避免现有项目因生成器升级发生隐式变化。
- 新`gear_event_battery_preview_idle`策略可配置档位事件页时长、电量预览时长、非充电常态页和充电常态页。
- 不新增tick状态机。时间模块按“档位事件”和“电量预览”角色申请独立资源，再由原有`show_mode`、`step_cnt`、`mode_change_show()`和`show_mode_change()`消费。
- 插入充电器和拔出充电器时，`mode_change()`立即清除旧页面计时并切换到对应常态页；调档事件仍只调用`show_mode_change()`启动档位显示。
- 充电常态电量、非充电常态档位以及非充电常态电量三种组合都在生成期收敛。无意义的“电量预览后仍停留电量”配置会被拒绝。
- 页面策略不修改电量映射、充放电追赶、充电真值表、显示扫描、PWM、AD_FAN保护和睡眠硬件配置。

## 27. 多PWM统一规划与固定占空比雾化

状态：`已确认并实现首版`

- PWM功能模块只声明物理脚、目标频率、时钟源、允许分频和用途；公共规划器统一选择Timer3或Timer4、具体通道、路由寄存器和周期值。
- HS2811 Timer3的PWM0到PWM4共用时钟源、分频和周期。共用Timer3的功能必须得到完全一致的时基计划，否则生成期拒绝；不能为了凑脚位偷偷修改任一功能频率。
- Timer4作为独立PWM资源纳入能力表，当前已确认`PC3/PA2/PA7`路由及`PWMSEL1`编码。F11类“PA7无刷250kHz + PC5雾化约108kHz”确定分配为Timer4和Timer3。
- 有刷/无刷兼容的两套电机PWM互斥，不能错误地按同时运行处理；雾化则必须分别与无刷路径、有刷路径检查共享Timer兼容性。
- 雾化运行逻辑沿用成熟`wh_deal()`函数边界和固定占空比结构，不新建运行时PWM抽象。`mode_change()`只处理依赖风扇、充电限制等状态归一。
- 关闭一个PWM通道时，只有同一Timer的其他通道均关闭才能清运行位。该规则同时覆盖雾化与有刷电机共享Timer3的场景。
- 配置必须提供明确的雾化按键动作，不允许生成启用但无法操作的输出；灯板没有`icon.mist`映射时不生成虚假角标。
- 旧的单PWM配置继续走原有确定路径，版本提升前已通过`main.c.in`字节级一致性测试。

## 28. 普通数字按键动作参数化

状态：`已确认并实现`

- 旧数字双键配置默认仍生成原有固定动作，不因新增配置能力改变源码；只有显式启用`features.digital_key`才进入通用动作组合。
- KEY1到KEY4按实际配置继续沿用成熟独立GPIO输入上拉、10ms消抖、约600ms首次长按和约60ms连续调档节奏，不新建扫描函数。
- 短按、双击和长按与AD按键共用同一动作集合和`KEY_deal()`动作生成规则，避免同一个产品动作维护两份实现。
- 双击只在配置要求时申请独立时间资源；第一击延迟、第二击执行、超时单击、长按取消及阻止睡眠的规则和AD按键一致。
- 普通数字键不生成`KEYx`变量，继续直接读取脚位宏；AD按键仍由ADC结果解码为原生`bit KEYx`，两种电气输入没有混在一起。
- 制冷、LED、雾化和连续调档动作在生成期检查对应功能和参数，不能产生按键有动作但输出模块不存在的源码。
- 新`digital_keys_active_low`允许连续的`KEY1..KEY4`；每个实际按键都独立申请GPIO和可选双击时间资源，并共同参与睡眠条件。旧双键输入类型继续锁定KEY1/KEY2，保证已有配置源码不变。
- 全部旧配置在版本提升前通过`main.c.in`字节级一致性测试。

## 29. 纯有刷固定占空比

状态：`已确认并实现`

- 纯有刷使用`motor.kind=brushed_fixed_duty`，只申请`FAN_ON`电机脚；该脚由公共PWM规划器根据物理脚能力分配Timer3/Timer4通道和路由。
- MCU运行代码继续使用成熟`AD_fan_deal()`函数边界，内部仅保留兼容版本已经验证过的有刷固定占空比分支：`base_count + fan_mode / gear_divisor`。
- 纯有刷不生成`PWM_FAN`升压脚、不申请`AD_FAN`、不生成`too_big_cnt`与16V保护，也不执行有无刷上电检测。只有该电机类型允许显式关闭`fan_voltage_protection`；任何无刷类型关闭保护均在生成期拒绝。
- 电量系统仍沿用成熟分段映射和充放电追赶结构，但直接使用配置中的一套有刷`fan_segments`与`cooling`补偿，不生成运行时电机类型分支。
- 按键、制冷、充电真值表、显示页面与扫描、电量映射/追赶、睡眠函数和时间资源均未改写。
- 示例采用`PC3/T3PWM2`、Fosc、周期寄存器147、约108.108kHz，以及`98 + fan_mode/4`占空比曲线；这些是可修改的产品参数，不是对所有有刷硬件的强制值。
